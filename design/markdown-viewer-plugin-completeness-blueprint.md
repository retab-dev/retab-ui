# Markdown Viewer Plugin Completeness Blueprint

## Verdict

The Markdown Document Viewer is plugin-complete for the bounded Retab UI
Markdown feature set described in this blueprint as of June 13, 2026.

It is a strong safe-GFM prose viewer with the core pipeline needed for release
notes, docs pages, generated reports, and parse output:

- GFM tables, task lists, strikethrough, autolinks, and footnotes
- hard line breaks
- math syntax and KaTeX rendering
- directive-based callouts
- GitHub blockquote alerts
- bounded directive and component markdown
- Mermaid diagram surfaces
- typographic transforms and emoji shortcodes
- sanitized raw HTML
- generated heading IDs
- syntax-highlighted code blocks
- source-faithful Text mode
- virtualized rendered/text pages

The target is not to install every plugin in the ecosystem. The target is a
complete, predictable Markdown document renderer for Retab UI: common Markdown
renders correctly, source mode is faithful, anchors are stable, and unsupported
syntax fails inertly instead of half working.

## Completion Target

The viewer should be complete for:

- GitHub-flavored Markdown documents
- generated prose reports
- docs-style Markdown
- markdown exported by LLMs
- markdown produced by Retab parsing/extraction flows
- GitHub blockquote alerts
- Mermaid and diagram fenced blocks
- typographic transforms
- emoji shortcodes
- MDX/component markdown through an explicit safe component registry

The viewer should explicitly not become a browser for arbitrary active HTML.
Every rich feature must have a bounded renderer, a sanitizer policy, and a
failure state.

## Non-Negotiable Contracts

- Rendered mode and Text mode must be separate products, not different views of
  lossy page markdown.
- Text mode must show the original source text for every line in the selected
  page, including frontmatter delimiters and blank-line spacing.
- Plugin output must survive sanitization only when it is part of the supported
  feature set.
- Every supported syntax feature must have renderer coverage, accessibility
  coverage, and at least one regression test.
- Heading anchor IDs must be generated by one algorithm across model, DOM, and
  fragment navigation.
- Unsafe links, images, scripts, event handlers, and active raw HTML must remain
  inert.
- Unsupported syntax must degrade to visible text or safe static HTML.
- Plugin additions must not break virtualization: no full-document render, no
  per-scroll parse, and no global DOM scan over all pages.
- Mermaid, MDX, and component markdown must run through whitelisted renderers,
  never arbitrary script execution.
- Typographic transforms and emoji replacement must be deterministic and must
  not alter code, math, raw HTML attributes, or source Text mode.

## Required Fixes

### 1. Make Text Mode Source-Faithful

Current issue:

- `createMarkdownDocument` rewrites YAML frontmatter into a fenced `yaml` code
  block for render mode.
- `createMarkdownPageContent` compacts page markdown from parsed blocks.
- Text mode renders `page.markdown`, so it loses frontmatter delimiters and
  collapses blank-line spacing.

Target:

- Each `MarkdownDocumentPage` carries both:
  - `renderMarkdown`: compact safe markdown for React Markdown
  - `sourceText`: exact original source slice for Text mode
- Rendered mode uses `renderMarkdown`.
- Text mode uses `sourceText`.
- Copy-all keeps using `document.text`.

Tests:

- frontmatter delimiters render verbatim in Text mode
- blank-line runs render verbatim in Text mode
- source-line highlighting still maps rendered compact markdown to original
  source lines

### 2. Unify Heading Anchor IDs

Current issue:

- The model computes heading IDs with its own slug logic.
- `rehype-slug` also writes DOM IDs.
- Renderer props can be clobbered by plugin-provided IDs.
- Fragment navigation matches model IDs, while DOM may contain rehype IDs.

Target:

- One heading ID function owns model, DOM, and fragment behavior.
- Either remove `rehype-slug` and let renderers own IDs, or configure/replace
  slugging so it shares the model algorithm.
- Renderer prop spread must not override the chosen ID.

Tests:

- headings with underscores
- headings with ampersands
- duplicate headings
- non-ASCII headings
- clicking a link to the real DOM heading ID scrolls to that heading

### 3. Add GitHub Alert Blockquote Support

Current issue:

- Directive callouts are supported:

```md
:::warning
Careful.
:::
```

- GitHub alert blockquotes are not first-class:

```md
> [!NOTE]
> Useful context.
```

Target:

- Add a remark transform for GitHub-style blockquote alerts.
- Normalize alert kinds through the existing callout kind vocabulary:
  `note`, `tip`, `important`, `warning`, `caution`.
- Decide whether `important` maps to `info` or becomes a sixth callout kind.
  Prefer adding `important` if the visual language can support it cleanly.
- Preserve normal blockquotes when the marker is absent or malformed.

Tests:

- each alert kind renders as a callout
- custom title behavior is deterministic
- ordinary blockquotes remain ordinary blockquotes
- source-line highlighting applies to the callout container

### 4. Define Directive Support Precisely

Current issue:

- `remark-directive` is installed, but only callout-like directive names are
  supported.
- Other directives may pass through in unclear ways.

Target:

- Treat directives as a documented Markdown component syntax.
- Support a finite directive registry, not arbitrary directive execution.
- Resolve directive names through the same whitelisted component registry used
  for MDX/component markdown.
- Unknown directives render as their textual content or safe fallback markup.
- Document the supported directive grammar.

Supported directive names:

```txt
note
tip
info
important
warning
caution
danger
tabs
tab
accordion
accordion-item
metric
badge
diagram
```

Supported grammar examples:

````md
:::note
Body
:::

:::warning{title="Production impact"}
Body
:::

:::tabs
:::tab{label="Python"}
```python
print("hello")
```
:::
:::tab{label="TypeScript"}
```ts
console.log("hello")
```
:::
:::
````

Unsupported:

- arbitrary directive-to-component mapping outside the registry
- executable widgets
- dynamic imports
- MDX-like props

Tests:

- supported callout directives render
- supported non-callout directives render through the component registry
- unsupported directives do not crash
- unsupported directives do not create unsafe attributes

### 5. Complete Footnote Rendering Policy

Current state:

- `remark-gfm` can produce footnotes.
- The sanitize schema allows footnote-related data attributes.
- Renderer styling is mostly inherited/default for footnote sections.

Target:

- Footnotes render with deliberate typography and spacing.
- Backrefs are keyboard-accessible and sanitized.
- Footnote section is visually compact and does not look like an accidental
  raw plugin dump.

Tests:

- footnote reference link exists
- footnote backref link exists
- unsafe footnote HTML remains inert
- footnote section does not break page measurement

### 6. Tighten Raw HTML Policy

Current state:

- `rehype-raw` parses raw HTML.
- `rehype-sanitize` removes unsafe output.
- Renderer includes safe support for tags like `details`, `summary`, `kbd`,
  `mark`, `figure`, and `figcaption`.

Target:

- Keep raw HTML support static and inert.
- Explicitly test the supported static tags.
- Explicitly test removal of scripts, event handlers, `javascript:` URLs,
  iframes, forms, and active embeds.

Supported static HTML:

```txt
details
summary
kbd
mark
sup
figure
figcaption
table-related tags
basic phrasing tags allowed by rehype-sanitize defaultSchema
```

Unsupported active HTML:

```txt
script
style
iframe
object
embed
form
input except GFM task-list checkboxes
event handler attributes
javascript: and data-script URLs
```

### 7. Add Mermaid And Diagram Rendering

Current issue:

- Mermaid fenced code renders as an ordinary code block.
- Other diagram code fences have no first-class visual treatment.

Target:

- Render `mermaid` fenced code blocks as diagrams in Rendered mode.
- Keep the raw diagram source available through copy and Text mode.
- Use a dedicated `MarkdownDiagram` renderer, not a generic executable HTML
  path.
- Keep diagram rendering client-only if the library requires browser APIs.
- Reserve stable dimensions before render so virtualization does not jump.
- Show a clear static error state when diagram parsing fails.
- Preserve code-block rendering for unsupported diagram languages.

Supported diagram languages:

```txt
mermaid
```

Future diagram languages must be added one by one with their own parser,
renderer, tests, and sanitizer policy.

Tests:

- `mermaid` fenced blocks render a diagram surface in Rendered mode
- invalid Mermaid source renders a non-crashing error state
- copy button copies the Mermaid source
- Text mode shows the original fenced source
- diagram render completion triggers page measurement
- unsupported diagram fences still render as code

### 8. Add Typographic Transforms

Current issue:

- Straight quotes, double hyphens, ellipses, arrows, fractions, and similar
  prose conventions render literally.
- Docs-style Markdown often expects typographic polish.

Target:

- Add a remark/rehype transform for safe typography in prose nodes.
- Transform text only in normal prose contexts.
- Do not transform:
  - inline code
  - fenced code
  - math
  - raw HTML attributes
  - URLs
  - Text mode

Supported transforms:

```txt
"quoted text" -> curly quotes
'quoted text' -> curly apostrophes/quotes where unambiguous
-- -> en dash
--- -> em dash
... -> ellipsis
<- -> left arrow
-> -> right arrow
<-> -> left-right arrow
1/2, 1/4, 3/4 -> common fraction glyphs where unambiguous
```

Implementation options:

- Prefer a focused local transform if the desired scope is small.
- Use an established unified plugin only if it can be configured to avoid code,
  math, URLs, and raw HTML attributes.

Tests:

- transforms apply inside paragraphs and list items
- transforms do not apply inside code blocks or inline code
- transforms do not apply in math
- transforms do not alter Text mode

### 9. Add Emoji Shortcodes

Current issue:

- Emoji shortcodes like `:sparkles:` and `:white_check_mark:` render literally.

Target:

- Add shortcode-to-emoji rendering for a stable GitHub-style emoji vocabulary.
- Keep unknown shortcodes as text.
- Do not transform inside code, math, URLs, or Text mode.

Tests:

- known shortcodes render as emoji
- unknown shortcodes remain literal
- shortcodes in code remain literal
- Text mode remains source-faithful

### 10. Add MDX And Component Markdown

Current issue:

- MDX/component markdown is not supported.
- Arbitrary MDX execution would violate the viewer's safety model.

Target:

- Support component markdown through a whitelisted component registry.
- Do not execute arbitrary user JavaScript.
- Do not import components by name from untrusted Markdown.
- Treat component blocks as declarative nodes resolved against an explicit
  `components` prop or internal registry.
- Unknown components render as safe fallback blocks that show the component
  name and source text.
- Component rendering must participate in measurement and virtualization.

Allowed component shapes:

```mdx
<Callout kind="info" title="Status">
Body markdown.
</Callout>

<Metric label="Accuracy" value="98%" />
```

Initial built-in component candidates:

- `Callout`
- `Tabs`
- `Accordion`
- `Metric`
- `Badge`
- `Image`
- `Video`
- `Diagram`

Hard safety boundaries:

- no arbitrary expressions
- no imports/exports
- no event handlers from Markdown
- no executable JSX expressions
- no access to ambient scope
- no remote component resolution
- no dynamic script injection

Implementation options:

- Prefer a restricted MDX parser path that extracts JSX element names,
  literal props, and children without evaluating code.
- If full MDX compilation is introduced, it must compile only against a frozen
  component map and reject expressions/imports/exports before evaluation.

Tests:

- whitelisted components render
- unknown components render safe fallback UI
- expressions/imports/exports are rejected or rendered inertly
- event handler props are rejected
- component render completion updates page measurement
- Text mode shows original MDX source

## Documentation Contract

The docs page should say exactly what is supported.

Recommended feature section:

```txt
Supported:
GFM, tables, task lists, footnotes, math, syntax-highlighted code, safe static
HTML, directive callouts, GitHub alerts, Mermaid diagrams, typographic
transforms, emoji shortcodes, whitelisted component markdown, source-faithful
text mode.

Not supported:
executable HTML, arbitrary directives, arbitrary MDX JavaScript, arbitrary
component imports, embedded apps, active iframes, remote component resolution.
```

Do not describe unsupported syntax as supported because a plugin happens to
parse part of it.
